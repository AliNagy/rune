01How to read this map

Two mechanisms move control between skills, and they are not interchangeable. Almost every confusion about Rune dissolves once you can tell them apart.

FollowDispatch
What happensthe current agent loads the skill into its own contexta fresh subagent is spawned and told which skill to follow
Context costpaid by the callerquarantined in the worker, which dies afterwards
Returnnone — it is the same agenta ≤200 token envelope; everything longer goes to disk
Written as“follow ai-report”a rune-dispatch block naming follow:
There is exactly one parent role. The main agent is the same writer whether it is running hello, init, vision, work, pause, handoff, or continue. Those seven are routes through one role, not seven agents — which is why pause and handoff writing the ledger does not break the single-writer rule.

02Four classes of skill

The follow/dispatch split, plus who is allowed to talk to the user, sorts all 28 skills into four groups. Two skills sit in more than one group, and both are flagged wherever they appear.

Route7 · user-invocable

The parent role. Reads state, talks to the user, dispatches everything else. Never reads source code.

hello · init · vision · work · pause · handoff · continue

Library5 · followed in place

Rules and schemas loaded into whoever needs them. Never dispatched, never a subagent of their own.

ai-root · ai-taskfmt · ai-ledger · ai-report · ai-serena

Worker14 · dispatched

One issue each, one fresh subagent each. Returns ≤200 tokens; everything else lands on disk.

ai-survey · ai-oracle · ai-triage · ai-bug · ai-decompose · ai-size · ai-execute · ai-verify · ai-land · ai-recover · ai-drift · ai-investigate · ai-research · ai-verify-finding

Protocol3 · bound by protocol.md

Type-specific planning rules. A decomposition worker loads whichever one the run’s immutable protocol record names — never one it inferred from a title.

ai-bug · ai-feature · ai-refactor

Two skills wear two hats. ai-bug is a dispatched diagnosis worker and a planning protocol — it reproduces the failure first, then governs how the fix is cut. ai-drift is followed in place by the executor (detect mode) and dispatched as a worker in four bounded modes.

Why continue touches almost everything. It is the only route that reconciles a dead session, and every phase can die mid-flight. 04The execution loop

What /rune:work actually does. Every box is a separate subagent with its own context; the parent only holds the ledger and the short returns.

Judgment fans out, mechanics do not. Decomposition gets 2–3 parallel planners because a bad cut does not announce itself — it surfaces later as executors colliding on files that were supposed to be disjoint. Running a command or writing a file from a settled spec gets one agent, because a second one returns the same string and costs the same again.

05The seven doors

The only skills a user can call by name. All seven are the same parent role — they read coordination state, talk to the user, and dispatch. None of them reads source code.

hello

Routethe front door

A router, and nothing else. Reads seven cheap files, decides where the request belongs, says where it is sending you and why, then hands over.

Triggers
/rune:hello, or any request where the user does not know which command they want.
Dispatches
Nothing. The shortest allow-list in Rune — two bounded probes, the named .rune/ reads, at most 20 top-level entry names, one question if genuinely ambiguous.
Writes
Nothing. The only possible write is ai-root’s bounded migration, internal to that skill.

State outranks intent

Some conditions answer the question regardless of what was asked — a deliberate stop, an open decision, or work in flight gets surfaced first, because the user may not know it is there.

It never classifies bug vs feature itself. That is the one distinction needing evidence from code, and it belongs to work’s triage dispatch.

init

Routeestablish ground truth

Mechanical, no interview, re-runnable. Finds and runs the pass/fail command that proves the codebase works, maps modules and conventions, flags danger zones, scaffolds .rune/.

Triggers
First use on a repo · vision finding no rune.yml · a re-run once setup measures stale.
Dispatches
ai-survey (work: survey) and ai-oracle (work: init/commands). Both because their output is unbounded and this is the session every other route starts from.
Writes
rune.yml · the empty schema-2 ledger.md · the .rune/ scaffold · one .gitignore line · the marked rune block in CLAUDE.md.

Staleness is measured, never judged

So two sessions looking at the same repository reach the same answer. Any one of these is stale:

  • the recorded commit no longer resolves in this repository
  • 50 or more commits since it
  • 25 or more files changed since it
  • the recorded oracle command is no longer in the project manifests

A stale verdict is a recommendation with its numbers shown, never an automatic re-run.

Write order is load-bearing. The ledger transition is persisted before rune.yml is installed, so the manifest can never claim initialization while the authoritative ledger still reads oracle: —. A crash between the two is a recognized state only init may finish.

Three rules. Never invent an oracle — if nothing verifies this codebase, that is the finding. Report confidence per item. Never fix anything: init observes, and repairs need acceptance criteria init has no mandate to invent.

vision

Routedecide what is being built

A conversation, not a generation task. The parent’s context exists for the interview — the one thing here that genuinely cannot be delegated.

Triggers
A project with no plan: a new idea with no code, or an in-progress codebase that has drifted.
Dispatches
ai-survey (Mode B only) · ai-decompose with work: vision/graph to write milestones.md.
Writes
vision.md and decisions.md, incrementally, as each section settles — plus the ledger’s vision phase.

Two modes

Mode A · new project walks seven topics in order, one at a time: what and why · the v1 line · shape · data · stack · constraints · done. The v1 line is the most valuable question in the interview and the one users most want to skip.

Mode B · in-progress surveys first, presents what actually exists including the awkward parts, interviews against reality, and produces the discrepancy table — intended vs actual vs gap. Each non-none row becomes a milestone or part of one.

Suggest. Never assume. Every choice with more than one defensible answer becomes a DEC-nnn record, and no milestone may be generated that depends on an open decision. That gate is what converts “make no assumptions” from a personality instruction into a checkable property. “You decide” is fine — recorded as decided with rationale: delegated to agent. Invisible delegation is not.

The phase marker is the ledger, not the file. vision: absent | drafting | complete lives in ledger.md; drafting is persisted before the first question and complete before graph dispatch, so a crash at any point is deterministic. The graph is generated from the files — anything that settled in conversation but never reached disk is invisible to the worker, which is a bug in the note-taking, not a reason to write the graph yourself.

work

Routethe execution loop

Triage → diagnose → plan → gate → size → dispatch → verify → land → reconcile. See §04 for the shape; this is what governs it.

Triggers
Building a feature, fixing a bug, refactoring, or advancing the current milestone.
Preconditions
PAUSED → stop and report · no rune.yml → init · no milestones and a broad request → vision · a specific request with no vision → proceed.
Dispatches
All nine worker types in the loop, plus ai-drift and ai-verify-finding.
Writes
ledger.md · assigned decision records · the run’s immutable protocol.md · atomic promotions of worker reports.

The permission list is derived from a reason

The parent exists to tell the user what is happening. Anything not needed to report status, route correctly, or record what happened is a dispatch — stated that way round on purpose, because a list of forbidden actions can always be stepped around by an action nobody thought to forbid. That is exactly how task files ended up being written in the parent’s context once.

The parent does not merge. That was once the single command it was allowed to run. It came off the list because a merge cannot be separated from what has to follow it: the suite is re-run against the merged tree, and if it fails the merge has to come back out. Only the first of those three is bounded — so the sequence is one ai-land dispatch, not a command with two dispatches around it.

One agent, one issue

Three bug reports is three triage subagents, never one holding a list. This governs scope, not concurrency — dispatching three at once is fine and usually right. It holds without exception because: evidence bleeds between issues and nothing in the returned text shows it; failure stops being isolated; a wrong answer cannot be attributed; and one agent holding three issues holds three working sets, which is the accumulation the ≤200 token rule exists to prevent.

The pre-reconciliation gate — always

Work stops after the draft fan-out and before any final task file exists. There is no flag that skips it. The ask is for additions, not “proceed?” — which only ever gets a yes.

  • Implementation assumptions, stated. Permitted only when internal, reversible, and unable to change behaviour, scope, acceptance, data retention, error semantics, or a public interface.
  • Exclusions, stated. Users often assume something is included.
  • An open question, not a yes/no. “Anything to add?” gets the thing they had been meaning to mention.

Anything user-visible found there becomes a parent-owned DEC-nnn, and planning restarts as a fresh run so every planner reads the settled input. Drafts built before their durable inputs existed are never reconciled.

When drift stops the loop

Measured, never felt. Stop and hand back to the user when any one holds:

  • N ≥ 3 — unfinished tasks retired
  • N / M ≥ ½ — share of the milestone retired
  • the drift record names the milestone’s own acceptance as invalid

Both numbers are written once, into the ledger’s quiescing entry, and never recomputed — so a later session reads the original measurement rather than re-deriving one from a tree that has since moved.

pause

Routestop cleanly

Stops the loop and leaves the repository in a state you can walk away from or take over by hand.

Triggers
“stop”, “hold on”, or a check of whether work is already paused. Running it twice is safe.
Dispatches
ai-verify and ai-land while draining · ai-drift in abandon mode, one per recorded worktree, after confirmation.
Writes
PAUSED · ledger.md to settle drained rows · assigned decisions and report promotions.
ModeIn-flight workUse when
drain defaultfinishes, verifies, merges — then stopsalmost always
abandonworktrees discarded, tasks reset to queuedthe current batch is going somewhere wrong
Why there is no “stop now”. Rune dispatches a worker and waits for its return. There is no channel back to one already running — no handle, no acknowledgement, no way to know a signal arrived. A mode claiming to interrupt live workers would promise something neither Claude Code nor OpenCode can deliver. What is real is that the flag goes down first, so nothing new starts; and whatever is already running has two honest endings: wait for it, or throw it away.

The invariant it guarantees: when pause returns, no task is left in_progress or landing. A paused ledger claiming work in progress is a lie about the state of the world, exactly as after a crash. Not a rollback — merged stays merged. Not a way to abandon a plan — milestones and task files survive.

handoff

Routemove to a fresh session

Most state is already on disk — that is the whole design. This skill exists for the part that is not: everything the user said, corrected, ruled out, or preferred, living only in a conversation about to end.

Triggers
Context above roughly 70% · a session drifted across several milestones · handing the project to someone else · a break long enough to forget the thread.
Dispatches
ai-survey in amend mode — one fact per dispatch, one dispatch at a time · plus ai-verify / ai-land if it has to drain first.
Writes
sessions/<stamp>.md · vision.md · decisions.md · ledger.md while draining.

Do not wait for the ceiling. A handoff written at 70% is thorough; one written at 95% is rushed and lossy, which defeats the point.

Triage of what is in your head

What you foundWhere it goes

The test: would this still be true and useful three sessions from now? If yes, it belongs in a permanent file. The handoff doc is for what stops being relevant once the work moves on.

Why the amend dispatches are serial. Two amend workers editing map.md at once would each preserve the file as they found it and silently discard the other’s edit. And never dispatch mode: full from here — a full survey re-derives the whole codebase to file a sentence, overwriting the map while doing it.

Rules. Never invent history — if you cannot remember why something was decided, say the reasoning is lost; a plausible reconstruction becomes fact the moment the next session reads it. Do not summarise the ledger. One handoff per session.

continue

Routeresume and repair

Everything comes from disk; nothing is remembered. Reconcile before reporting — a ledger left by a dead session contains claims that are no longer true, and reporting them as status propagates the lie.

Triggers
A fresh session, a crash, or a cleared context.
Dispatches
ai-recover · ai-drift · ai-verify · ai-land · ai-bug · ai-size · ai-decompose · ai-investigate · ai-research · ai-verify-finding.
Writes
ledger.md repairs · recovered decisions · report promotions · deletes PAUSED only on a confirmed resume.
  1. Read state — the cheap coordination files only. Never source, never a task file unless about to act on it.
  2. Validate or migrate the ledger. Schema 2 must validate completely; schema 1 and schema 0 have migration paths; an unknown schema stops. A nonempty legacy ## Amendments footer on an unfinished task fails closed into a migration drift record — the only pre-migration worker dispatch there is.
  3. Reconcile the vision phase from the ledger field, never from file shape.
  4. Reconcile report assignments first — every pending or blocked DRF-/INV-/RES- slot, by file order rather than guesswork.
  5. Reconcile diagnosing rows before executable ones. No task file exists yet, so they must never reach ai-execute or ai-recover.
  6. Every in_progress row is a lie — nobody is holding it. Resolve each by the table below.
What is on diskAction

no handoff · empty diff · branch aheadpending, resume_at: publish
no handoff · empty diff · branch not aheaddispatch ai-drift discard-empty

It also sweeps: orphaned worktrees → ai-land cleanup; stale verifying and landing rows; interrupted decomposition runs; unregistered replan transactions; unsized rows → ai-size; mitigation-repair assignments; staged worker questions (assigned DEC ids serially, in numeric order); and unverified claims → ai-verify-finding.

Discard freely. Under Serena a fresh executor re-acquires its working set for about 10k. Partial work of unknown provenance is worth less than the clean base it is occupying — the task file, not the worktree, was always the durable state. The exception is a bug’s diagnosis_commit, which is durable evidence and is preserved as the task baseline.

It does not start work. Reconcile, report what was repaired, hand to work or vision. Continue answers where are we; the other routes answer what next.

06Parent libraries

Followed in place, never dispatched. These carry the rules that would otherwise have to be repeated in every skill that depends on them.

ai-root

Librarycoordination-root identity

The single seam for “which .rune is canonical, and can the legacy .agent/ directory be migrated safely”. Followed by all seven routes before any coordination read or write — init, vision, pause, handoff with mode: initialize; hello, work, continue with mode: resolve.

Filesystem stateResult
both .rune/ and .agent/ existstop — report both absolute paths, change neither
only .rune/resume any marked migration, return it
only .agent/validate ownership and worktree safety, then migrate
neither, initializecreate it, ensure worktrees/ is ignored, return
neither, resolvereturn the path without creating it

Filenames are not ownership. The generic name may belong to another tool, so migration requires at least one independent Rune signal — an initialized rune.yml, a recognizable ledger, a # Vision / # Decisions pair, a # Map — <project> record, a session handoff or PAUSED record, or an artifact matching an ai-taskfmt schema. Unknown top-level entries make ownership ambiguous, and it stops rather than guessing.

Registered worktrees block the rename. One bounded probe counts worktrees at or below the legacy root; any positive count stops migration rather than stranding Git metadata and possibly live work.

Migration is resumable through a durable marker (prepared → rewriting) and an exclusive lock directory that moves with the rename. A failed run leaves both in place, so partial state can never be mistaken for an available migration; locks are never stolen or aged out. It never does a global text replacement — only exact absolute legacy paths, enumerated pointer fields, Markdown link targets, ledger pointer columns, and the exact .gitignore line.

ai-taskfmt

Librarythe spine

The largest skill in Rune and the one everything else references. Every durable fact lives on disk under .rune/; no agent may rely on conversation memory for anything another agent will need. Assume every reader is a stranger with an empty context.

What it owns

  • every file schema — task file, milestone, decision record, planner draft, replacement map, handoff note, progress file, vision document
  • the dispatch envelope — follow, work, attempt, main_root, worktree_path, pointers, reports
  • the return envelope — work, one-line summary, worktree, one outcome field, ≤200 tokens with no per-job exceptions
  • the single-writer table, and the concurrency rule that generates it
  • the checkout identity contract — current working directory is never an identity
  • report staging and atomic no-replace promotion
  • findings — a claim is not a fact until a fresh subagent confirms it
  • the published artifact interface — base_commit / artifact_commit / verified_commit
  • bounded state probes, listed by name per skill so qualifying is a lookup, not a judgement call
Pointers, not payloads. The parent names where things are; the worker reads them itself. Passing content down means the parent had to hold it first — the exact cost the whole system exists to avoid — and it keeps every dispatch the same size no matter how big the job is.

ID spaces never collide. M- milestone · T- task · DEC- decision · DRF- drift · INV- investigation · RES- research · FND- finding. Local planning ids — R-nnn run, P-nn planner slot, D-nnn proposed task — never enter the final namespace.

Ids are burned permanently. An unused, blocked, or interrupted reservation is never recycled, because a late worker may still hold its staging pointer. Gaps are the correct outcome, not a bookkeeping failure.

ai-ledger

Librarymutable routing state

ledger.md holds all authoritative mutable routing state. One writer: the parent. Workers never touch it — they report, the parent records. This skill owns what the statuses mean and what the file looks like; the routes own the procedures.

The task row

id · milestone · title · status · blocked_by · worktree · attempts (dN/eN/vN/lN) · failures · latest_finding · blocker · resume_at · replaced_by

Counters are incremented in the same update that claims the phase, before dispatch — so a worker that dies still visibly consumed an attempt. failures counts verifier fail verdicts only; unverified, landing failures, and dead dispatches do not raise it.

Atomic transitions

  1. Re-read and validate the complete ledger at its declared schema.
  2. Produce one candidate containing every changed field plus the returned dispatch row.
  3. Validate the candidate, then replace ledger.md in one write.
  4. Only then dispatch the next worker.

Never write status first and fill in its required fields later — a crash between those edits creates a state no fresh session can route.

Log every dispatch — the point is not the audit trail. It is that absence becomes visible. Reconciled task files with no planner and reconciler rows means the parent wrote them; a commands phase with no ai-oracle row means the parent ran the suite; a survey with no ai-survey row means the parent read the codebase. Each of those was a real defect in Rune before this table existed — and otherwise almost impossible to notice, because the files all exist and the ledger looks healthy.

## Drift is routing state — a quiescing entry freezes its closure and suppresses every new dispatch for those ids. ## Findings is a record, never routing state — findings block nothing, gate nothing, and refuted entries are kept permanently on purpose.

ai-report

Librarytalking to the user

Two rules govern everything: report at the moments that matter, and say it in the fewest words that stay accurate.

Speak at these points and not between them: a task finished and was verified · a milestone completed · a batch was dispatched, and again when it lands · the plan turned out wrong in a way that affects other tasks · something needs a decision · work stopped, for any reason. Between them, stay quiet — no narrating dispatches, tool calls, or reasoning in progress.

Every report opens with a TL;DR of two or three lines: what happened, what is next, what needs them. A reader who stops there should still know where things stand and whether they are needed.

Only report a confirmed finding. A claim still waiting on its verifier is not news, and telling the user makes them act on something nobody has checked. Refuted findings are not reported at all — somebody guessed wrong and a second agent caught it, which is the system working.

ai-serena

Libraryreading code without spending the budget

Followed by every worker that reads code. ai-execute loads it explicitly; ai-triage, ai-survey, ai-decompose, ai-size, ai-investigate, ai-verify-finding, and ai-refactor all invoke it by name.

Agents do not blow budgets reading what they need. They blow them exploring.

The ladder — stop at the first rung that answers the question

  1. get_symbols_overview(file) — what is in this file. Almost always enough to orient.
  2. find_symbol(name_path), include_body=false — where a thing lives, its shape.
  3. find_symbol(…, include_body=true) — the actual code, one symbol at a time.
  4. Read(file) — last resort. Justify it.
Instead ofUseWhy

Never read a file “to get orientated.” Orientation comes from map.md, which exists precisely so nobody re-derives it. A missing or stale map is an init problem, not something to solve by browsing.

Budget discipline. At roughly 60%, stop taking on new ground: finish the step in flight, write the handoff, return. Returning early with a good handoff is a success. Running out of context is not.

07The workers

Fourteen skills, each dispatched as its own subagent, each carrying exactly one issue. None of them can talk to the user; none of them writes the ledger.

ai-survey

Workermap the codebase
Dispatched by
init · vision Mode B · handoff (amend)
Writes
map.md (sole writer) and Serena memories
Returns
survey: mapped | amended | unchanged | conflict | blocked

Always a subagent. Surveying burns context by design; that cost is quarantined in a worker that returns a digest and dies.

mode: full — breadth before depth

A surveyor that starts reading files in src/ learns a great deal about one corner and nothing about the shape. Perimeter → entry points → module map → conventions (sampled; report what the code does, not what a style guide says) → danger zones → completeness.

That last pass is the most valuable output on an in-progress codebase: stubs · orphans (no inbound references) · half-wired paths · contradictions (two implementations of one concept) · abandoned directions. Each with a file reference, stated as observation with evidence. “AuthService.refresh returns null and has no callers” is useful; “the auth is a mess” is not.

mode: amend — one fact, and usually no write at all

What it foundReturnsWrites
the fact is not thereamendedadds it in the right section
already there, in substanceunchangednothing
the map contradicts itconflictnothing — quotes both lines

A conflict is not the worker’s to resolve. It has one sentence from a conversation it did not see; the map has a line somebody surveyed the codebase to write. Only the user knows which is true. Three of the four outcomes write nothing, and that is normal — overwriting a surveyed observation to make a dispatch look productive is the failure this mode is most likely to produce.

ai-oracle

Workerfind and run the pass/fail check
Dispatched by
init (work: init/commands). Its rules also apply inside ai-verify and ai-land without a separate dispatch.
Writes
notes/init-commands.md — full output, every command, exit codes
Returns
oracle: passing | failing | none plus per-command verdicts and durations
Why it exists. Rune executors grade their own homework, in a context nobody else can see, and models are optimistic. Without an independent check you get a ledger of green rows over a codebase that does not run.

Run it, do not infer it. A command in package.json proves nothing about whether it works in this checkout, on this machine, today. Inference is what the dispatcher could already do for free; running it is the entire reason this is a separate dispatch.

Two oracles

Project-global — “did I break anything else”. Established once, recorded in rune.yml, run after every task. Task-local — “did my specific thing work”, produced by the task. A project with no test suite still accrues one, task by task, through the local oracles: that is what makes degraded mode survivable rather than hopeless.

Three outcomes

  • passing — normal operation; the regression check for every task.
  • failing on arrival — record the exact known-red baseline. A task regresses only by adding a failure not in it. Getting the suite green is legitimate work — propose it as a milestone, do not smuggle it into an unrelated task.
  • none found — say so loudly, oracle.status: none, degraded mode. Deliberately noisy, so the absence is felt on every task rather than forgotten by task three.

Vacuous checks are the most common way verification silently fails: a test asserting nothing or asserting true; a subject mocked so thoroughly only the mock is exercised; a behaviour test added after the change and never observed red; a refactor whose baseline was never run. Absence of proof is not proof — that is unverified, not pass.

Governing rule: no fix without a failing reproduction. Not a description of the failure. Not a stack trace. An executable case that fails now and will pass after.

Identity comes before diagnosis. The parent reserves T-nnn, writes the run’s immutable protocol.md with reserved_task, and adds a diagnosing ledger row before dispatch. The worker then creates or validates that exact worktree before writing anything. It never reads the ledger or allocates an id.

  1. Reproduce. Establish the failing case as code. Confirm it fails now, capture the exact output, and establish the boundary — what inputs fail, what adjacent inputs succeed. A bug you can only trigger one way is under-characterised, and you will not know if the fix was general.
  2. Root cause, not symptom. The reproduction tells you where it surfaces; that is rarely where it is caused. Ask “why is the input wrong” one level up until the answer is “because this code is wrong” rather than “because it was given bad data”.
  3. Commit the reproduction on the task branch and record diagnosis_base_commit and diagnosis_commit. Red-then-green is free here — red was observed in step 1, before any production change existed.

Symptom fixes are identifiable: null-guards at the point of crash, try/catch around the failing call, defaulting a value that should never have been absent. If the fix tolerates bad state rather than preventing it, it is a symptom. Sometimes that is the right call — but it must be explicit: remediation: mitigation with root_cause_followup naming a separate root-cause task. Diagnosis may recommend it; it never silently authorizes it.

diagnosis_commit is not an artifact. It has no artifact_commit, cannot be verified, and cannot be landed on its own — verification and landing must refuse to treat it as completed work. It is the starting baseline the eventual publication range contains.

Watch for misclassification. Triage guessed from a sentence; you have now looked at the code. Two common corrections: it was never implemented (a feature — features need decomposition and possibly decisions, bugs do not), and it works as designed and the design is wrong (a decision to surface, then a feature or refactor). A failed or reclassified diagnosis burns the reserved id forever, so a late return cannot attach evidence to a different task.

Why just-in-time. A task must name real files and real symbols. Cutting rules

  • Behaviour-changing work is vertical (red_then_green). “Token rotation end to end” is a task; “all the interfaces, then all the implementations, then all the tests” is three tasks of which none can demonstrate the change alone.
  • Refactors are horizontal (green_baseline) — additive, then mechanical, then subtractive. Every intermediate state compiles and preserves the same baseline.
  • Characterization is a separate test-only task when a refactor has no adequate net.
  • Ceiling: 5 files, one subsystem, one verifiable outcome.
  • Independence over elegance. Two slightly redundant tasks that run in either order beat one clever task that couples them — redundancy costs tokens, coupling costs correctness.
The forbidden list is the one that matters and the one planners skip. Executors do not blow budgets reading what they need — they blow them exploring. The planner is the only agent positioned to know that src/api/** is irrelevant to this task and would cost 40k tokens if opened. The executor cannot know that, and will look, because looking feels responsible. Always give the reason: src/legacy/** — being deleted in M-05 tells the executor it is not missing something; a bare path makes it wonder.

Planners cut independently. Where independent cuts agree, the milestone divided cleanly; where they disagree, that seam is the genuinely hard part. A planner that hedges toward what it imagines the others will produce erases exactly the information the fan-out was dispatched to buy. No planner registers tasks in the ledger — the parent is its sole writer.

What actually makes a task too big

Not line counts. Breadth of the change surface · how much must be understood before anything can be written · decisions still open inside the task (“handle the error appropriately” is a question, not a step) · sequencing assumptions the file does not state · the whole lifecycle including the failing check and the handoff · how likely it is to need work outside its declared surface.

Headroom is the point. Ask whether it fits with the first approach failing. If the honest answer is “yes, if nothing goes wrong”, that is a split.

When in doubt, split. A wrong split costs one more planning round. A wrong pass costs a burned executor, a partially implemented task, a worktree somebody has to reconcile, and often a change that crossed its declared surface to get finished — none of which surfaces until the context is already gone.

Your verdict gates dispatch, so do not hedge it. There is no “pass with concerns”. A split must name the seam, which part comes first, and what the second depends on — otherwise it is just an objection.

It is stateless. Before touching source it reads whatever exists — and two of those files are the ones people skip:

  • notes/T-nnn.verify.md, last block first. The task came back from verification. Answering the last block is the work. Running the original steps again earns the same verdict a second time — which is how a task reaches two failures and lands on the user’s desk with nothing learned.
  • notes/T-nnn.landing.md. The task was verified and then broke the main tree on merge. That record holds the exact failures, quoted, and whether they fell inside the declared change surface.

Both can exist at once — they fail at different gates, and the later one is the live problem.

Two checkout identities, bound first

main_root must resolve to itself; worktree_path must be a registered worktree of the same repository, on task/T-nnn. Never search for a similar worktree, accept the harness’s current directory, or allocate a new path on a retry. The ledger path is the task checkout.

Source into the worktree; coordination into <main_root>/.rune/. The progress file, handoff, drift and decision records must be visible to the dispatcher, the verifier, and the next session before anything merges. Written inside the worktree they would appear only on merge — which is precisely when nobody needs them any more.

The rules that hold because you keep them

  • Stay inside your change surface. Adapt freely within it; stop the instant the work requires a file the task did not name.
  • Edit first, then tick. If you die between the two, a missing tick self-heals — the next executor finds the step already applied. The reverse order leaves a tick with no edit, which makes the record lie and causes real work to be skipped.
  • Stop at ~60% of budget. Finish the step in flight, write the handoff, keep the worktree, return budget.
  • Never mark yourself done. A separate verification decides that, in a context that never saw your reasoning.
  • Never widen scope to be helpful. An unrelated fix lands unreviewed, unverified, and outside every acceptance criterion in the ledger.

Publishing — done means a commit exists

Stage only declared files, commit on the task branch, prove base_commit is an ancestor of artifact_commit, the range is non-empty, and the worktree is clean — then append the publication block. Never replace an earlier one: verification failures and landing failures send a task round the loop, and each attempt must say exactly which immutable range it produced.

Noticing something outside your task has exactly three readings: it makes the task’s plan false → drift; it needs a user choice → question; it is simply noticed and the task works either way → write a claim to findings/open/ and carry on. Writing it down is the whole of your involvement — do not look into it, widen your surface to check, or fix it.

ai-verify

Workerthe independent check

Three hard rules. Verify in a clean context — you must not have the executor’s reasoning, only its artifacts. Never verify your own work. And exactly one task per agent — a batch of three produces three correlated verdicts, because after passing the first two it is judging the third against its own accumulated sense of what this batch looks like rather than against the spec.

It does not read the executor’s summary. That is the claim under examination, and reading it primes you to agree with it.

Eight steps, run in full on every attempt

  1. Bind to the published artifact. HEAD equals artifact_commit; worktree clean; base_commit an ancestor; the diff non-empty. From here, “the diff” means only that range.
  2. Does the diff match the declared change surface? Files outside it are a finding, not a detail.
  3. Run the task-local check. Its declared after-result must hold.
  4. Check the declared evidence mode is present, matching, and internally consistent.
  5. Hunt vacuous checks using the mode — including a revert-sensitivity probe in a disposable worktree where one is cheap. Never mutate the artifact you are verifying.
  6. Run the project oracle in the worktree, against the known-red baseline — not against zero failures.
  7. Audit the ticks. Spot-check two against the diff. A ticked step with no corresponding change means the record is lying, and the next executor would skip real work.
  8. Walk the acceptance criteria one at a time. No partial credit, no “essentially done”.

Why all eight even on attempt 4. Narrowing to “did they fix the last finding” is how the second defect in a task ships: the executor answered the finding, you confirmed the finding was answered, and nobody looked at the rest.

Write the record before you return. A fail that exists only in a return value dies in the parent’s context — and the next executor reads the task file, the handoff, and the diff, none of which say why the last attempt was rejected. It would repeat that attempt move for move. A pass block is written too; it is what closes the chain and lets a later reader tell a resolved history from a live one.

A false pass propagates into every task built on top of it, and by the time it surfaces nobody knows which of the green rows was the lie. You are not a reviewer — no style comments, no improvements, and above all no fixes: a verifier that fixes what it found has destroyed the only independent check in the system.

ai-land

Workermerge the exact verified commit
Dispatched by

Writes

Returns

The only worker allowed to change the main tree. Every other worker is confined to a worktree — so this is the one place a mistake is not contained by a worktree boundary. The sequence is fixed for that reason: do not improvise inside it, and do not add a step because the situation seems to call for one.

Why landing is not the last step of verification. The verifier proved the task against the tree it was cut from; a merge into a tree it never saw is a new claim needing new evidence. Two tasks can each pass verification and still break the project together — task A renames something task B calls, neither touches the other’s files, git merges both without complaint.

  1. Main tree clean outside .rune/. Otherwise a rollback could not tell stray source changes from the merge. → stuck.
  2. Bind to the verified artifact. Latest verdict pass; commits match the latest publication; verified_commit equals artifact_commit; the range is non-empty. Any mismatch → refused, touching nothing.
  3. Record the rollback point. One line, captured before anything is touched.
  4. Merge the SHA — never the branch name. The branch is checked only to prove it still names the artifact; the SHA is what passed verification.
  5. Run the project oracle in the main tree. Skipped only on a genuine fast-forward — a git fact you check, not a call you make.
  6. On failure, roll back first, record second. Same write-order rule, same reason: a missing record is recoverable, a record with the bad merge still in the tree is not.
  7. Run the oracle again to prove the rollback restored the tree.
  8. Record success, then clean up. Cleanup is last because the worktree is the recovery asset for every earlier failure.
Never undo the merge with revert -m 1. It leaves the merge in history, so git treats the branch as already merged — and the fixed worktree would then land as an empty diff. Re-landing the same branch is the entire point of the loop, and that one command quietly breaks it.
Step 7 is the one most worth not skipping. A rollback assumed to have worked and did not leaves main red while your return value says green — the exact failure this skill exists to prevent, moved one step later where nobody is looking for it.

Escalation: ordered rules, first match wins

Nothing asks whether the fix “seems to be converging” — that was a judgement two agents could answer differently from the same record. main: red stops everything: no task claimed, no batch started, nothing landed. It is cleared by a human, not by the next agent that finds it inconvenient.

The tripwire

Adapt freely inside your declared change surface. Stop the moment the fix requires a file the task did not name. The boundary is drawn at files rather than judgement so it cannot be rationalised away under pressure.

  • signature differs from what the spec assumed, but the file is yours → adapt, note it, continue
  • a helper you expected does not exist, and you can add it inside your surface → adapt
  • the fix requires editing a file outside your change surface → stop
  • the fix requires reading something on the forbidden list → stop
  • the task’s premise is simply false → stop

“I had to leave my sandbox” is exactly the signal that the plan needs revisiting, not just this task.

Stopping properly — three things, in this order

  1. Write the drift record to the assigned staging path. invalidates is the load-bearing field: you are the only agent who has seen this, so name every downstream task whose premise it breaks.
  2. Write the handoff for a stranger with an empty context — no “as discussed”, no pronouns pointing at a conversation that will not exist.
  3. Discard the worktree.
Why the worktree goes even when a step looks useful. A drifted task’s contract will be retired and any replacement gets a new id, branch, worktree, and evidence chain. Keeping or transferring the old diff would make source written for T-016 appear under T-020 with no truthful publication history. Name the useful step in the handoff instead; the replacement implements and verifies it under the new contract.

Asking the user has its own tripwire: ask only when the answer changes behaviour the user would notice and neither the task spec nor an existing convention settles it. An agent that asks about things it could have determined is worse than one that guesses, because it spends the user’s attention — the scarcest thing in the system. Always give a recommendation.

ai-investigate

Why it exists: a system that only knows how to make plans will turn “why is this slow?” into an implementation plan. That is the failure mode this protocol prevents.

Step 1 is making the question answerable. “Why is the dashboard slow” → “which operation dominates dashboard load time, and by how much”. “Is the auth secure” → too broad; narrow it or split it. State the question at the top of the output — if the answer does not address it, you drifted.

Running things is allowed. Changing them is not. The suite, a profiler, a read-only query, a build — all fine. No source edits, no test edits, no package installs, no migrations, no “just try” a fix to see if it helps. Scratch files go outside the working tree. No worktree. No diff. When you are done the tree is exactly as you found it.

Outside evidence goes through exactly one of: the reserved RES-nnn assignment (load ai-research and follow it), or a recovery pointer to an already-promoted RES report. Never improvise research — a remembered fact presented as a looked-up one is precisely what both protocols exist to prevent.

Four mandatory sections: answer · evidence · confidence · what I did not check. The last two are what make an investigation trustworthy: one that reports uniform certainty over a codebase it sampled is worse than one that names its blind spots, because the reader cannot tell which parts to re-check.

It does not schedule work. Proposed next steps are proposals — they do not enter the ledger, do not become task files, and get no T- id. The gap between “here is what I found” and “I have begun changing your codebase” is the entire purpose of the protocol.

ai-research

Writes

Governing rule: every claim traces to a source you actually retrieved, and every source is graded. An ungraded claim is an opinion wearing a citation.
The exact failure it exists to stop. A model asked a factual question will answer from training data, write it in the confident register of something looked up, and attach a plausible-looking link it never opened. The answer is often roughly right — which is what makes it dangerous. It is wrong in the details that made the question worth asking, and nothing in the output distinguishes it from real research.

It names no tools and must not be edited to name any — Rune runs under more than one harness. It requires three capabilities: search, retrieve, record. If the first two are unavailable or blocked, it stops and says so.

The discipline

  • Fix the question first — scope, inclusion criteria, what would change the answer, and a budget, all before the first query. Searching first guarantees the question drifts to match what you happened to find.
  • At least five distinct formulations: plain language · term of art · the negative case (mandatory — advocacy is over-published and criticism under-indexed) · primary source · time-bounded · adjacent field.
  • Follow the citation graph both ways — backward to what a good source cites, forward to the retraction, correction, or advisory filed since.
  • Grade every source on five tiers. Tier 5 is not evidence — it may be a lead. Tier is per claim, not per domain: a vendor’s docs are Tier 1 for what their product does and Tier 5 for whether it beats a competitor.
  • Triangulate, and check independence properly. Ten pages saying the same thing usually means one origin and nine copies. Shared origin, author, funder, or wording means one source with two mouths.
  • Spend part of the budget trying to break your own answer — real queries, run after you know your conclusion, aimed squarely at it.
  • Stop on saturation or budget, and record which. Stopping because you found an answer you like is not a stopping rule.

Fabrication rules are absolute: never cite a source not retrieved this session · never reconstruct an address from memory · load-bearing claims carry a verbatim quote · mark every statement sourced or inferred · training data is a lead generator, never a source · if retrieval is unavailable, stop.

Five mandatory sections: answer · certainty · what contradicts this · what I could not establish · search log. An answer with uniform confidence, nothing against itself, and no way to re-derive it is exactly what a fabricated one looks like — so a real one must be visibly different.

ai-verify-finding

Workercheck a claim somebody else made

The one qualification that matters is that you were not there. You did not write the code the claim is about, you have no memory of reading it, and you have nothing invested in the claim being right. The finder had all three — which is exactly why it could not do this itself.
  1. Restate the claim as something that can be false. “The purge query sweeps sessions with a null expiry” can be checked; “the session code is fragile” cannot — and that is inconclusive, because it was never a claim.
  2. Look at the actual code, narrowly. You are answering one question, not reviewing a subsystem.
  3. Try to prove it wrong first. A claim that survives a genuine attempt to refute it is worth something; a claim you only tried to confirm is worth nothing, because you would have found supporting detail either way.
  4. Run a cheap check where one settles it — in a scratch location, then thrown away. Do not add it to the suite; that is a task, and tasks go through decomposition.
  5. Decide, and say what would change your mind.

refuted is the most valuable of the three. It is the one that stops a wrong belief from being planned against for the next three months — which is why all three verdicts are promoted and kept permanently.

Narrow the claim rather than failing it. “Purge deletes sessions that never expire”, when it only does so with a default-off flag on, is confirmed with the claim restated to what is actually true.

Never soften a refutation. “Technically not true, but a reasonable concern” is a confirmed finding wearing a disguise. If the claim is false, say it is false and say what the finder missed — the finder is not owed a consolation prize and the user is owed a straight answer.

08Planning protocols

Loaded by a decomposition worker, never dispatched on their own. Which one binds is decided by the run’s immutable protocol.md — not by the request’s wording and not by the milestone title.

ai-bug

Protocol

No fix without a failing reproduction. By the time the task is written, diagnosis — the expensive half — is already done, so most bugs are one task. A second task appears only when a mitigation is accepted, or when the cause spans subsystems.

verification: red_then_green

Acceptance always includes the boundary cases from the reproduction — that third line is what stops a fix that special-cases the one input you happened to try.

ai-feature

Protocol

Vertical slices, not horizontal layers. “All the interfaces / all the implementations / all the tests” is three tasks of which none can be verified alone, and the whole milestone stays unverifiable until the last one lands.

verification: red_then_green

Features fail by expanding — “add user profiles” quietly becomes avatars, then image upload, then a CDN decision. Write the exclusions down; they become the milestone’s out: scope and the tasks’ forbidden entries.

The first slice is the thinnest end-to-end path — one field, one route, one test. It validates the design against real code before four tasks are built on an assumption. Every feature task also names its integration point, or it produces an orphan the next survey flags as abandoned work.

ai-refactor

Protocol

If you had to change a test, it was not a refactor. That is the whole discipline; everything else is machinery for making it true.

verification: green_baseline

Require the safety net first. A refactor with no coverage over the affected code is a rewrite with extra steps and no way to know it worked. If coverage is absent, the first task is a characterization task — tests that pin current behaviour whatever it is, including behaviour that looks wrong. Pin it as-is and file the bug separately; fixing it during a refactor destroys the only signal you have.

Acceptance is inverted: the existing checks pass, unmodified, and no test file appears in the artifact diff. That line is mechanical and it is the point.

Additive → mechanical → subtractive, one kind of change per task, with the deletion task last and separate — it is the only irreversible one, and the one you want to be able to skip if something surfaces.

10Four walkthroughs

The same machinery, traced through the four paths that actually happen.

A bug, end to end

  • ai-triage — work: request-1 → type: bug
  • parent — reserves T-014, writes protocol.md with reserved_task: T-014, adds a diagnosing row with d1 and the absolute worktree path
  • ai-bug — creates .rune/worktrees/T-014 on task/T-014, commits the failing check, records diagnosis_base_commit + diagnosis_commit → reproduced
  • ai-decompose × 2–3 — each reads the same protocol and the committed reproduction; exactly one proposed task is marked reservation: primary
  • the user — gate: sees the candidate cut, the assumptions, the exclusions, and is asked what to add
  • ai-decompose × 1 — maps primary onto the already-reserved T-014; allocates ids only for extra tasks. The parent registers rows; T-014 moves diagnosing → unsized, keeping its d1
  • ai-size — pass → the row becomes pending and is dispatchable
  • ai-execute — reconfirms red before the first production edit, then publishes base_commit..artifact_commit
  • ai-verify — proves the published range contains the diagnosis commit → pass, verified_commit
  • ai-land — merges that exact SHA, re-runs the oracle → landed, main: green

A feature that hits a question

  • ai-triage → ai-decompose × 3 → gate → reconcile → ai-size × N — the ordinary path
  • ai-execute — hits a choice it has no authority to make. Writes decisions/open/T-017-e2.md with no id, keeps the worktree, returns status: question
  • parent — assigns DEC-nnn, moves the record into decisions.md, deletes the staging file, sets the row awaiting, and asks the user. The rest of the batch keeps running.
  • the user decides — the row returns to pending; a fresh executor picks up the handoff, the worktree diff, and the now-resolved decision
Why the extra hop. Three executors run at once, so a shared append target races — and both would reach for the same next id. And a question that exists only in a return value dies with the worker, while the work survives in the kept worktree. The question has to survive on the same terms.

Drift and replan

  • ai-execute — returns drifted: staging record written, worktree discarded
  • parent — promotes the record, then in one ledger update adds a quiescing entry naming the exact frozen closure plus closure: N of M unfinished, and drift-blocks every inactive row in the set
  • ai-drift quiesce · ai-land drift-observe — drain each frozen row by its pre-freeze state. No frozen return may trigger a new verifier, retry, diagnosis, or lander
  • ai-decompose × 2–3 → gate → reconcile — a fresh R-nnn whose protocol carries drift: DRF-003 and retiring: [...]; the reconciler writes new task files and replacements.md
  • parent — one atomic transaction: new rows added and old rows moved to retired with their replaced_by lineage. If it fails, nothing retires and nothing becomes executable
  • ai-size × N — every replacement is sized like a first cut, because a replan is not evidence the new cut fits

Crash recovery

  • ai-root — resolve; finish any interrupted directory migration
  • parent — validate or migrate the ledger (schema 0 / 1 → 2); an unknown schema stops here
  • parent — reconcile report slots by file order: pending · recorded · unused · blocked
  • ai-bug — re-dispatched only when a diagnosing row has no terminal diagnosis block
  • ai-verify · ai-drift · ai-recover — one per in_progress row, chosen by what is actually on disk
  • ai-land — cleanup for orphan worktrees; a re-dispatch for a stale landing row that may or may not have merged
  • ai-size · ai-verify-finding · ai-decompose — unsized rows, unverified claims, and mitigation repairs swept last
  • parent — report what was repaired, not just what exists, then hand to work or vision

12Invariants and concurrency caps

The rules that hold across every skill. Most of them are here because breaking them is easy and the damage shows up somewhere else, in a context that cannot see what you did.

Context is the budget

The main session never reads source code — one “just checking” file read brings back the exact cost the design exists to avoid. Subagents return 200 tokens or less; anything longer goes to disk. An agent in trouble writes a handoff and exits rather than pausing, because resuming an agent keeps its context, which is the opposite of what you want.

Changes before records

Always make the edit, then tick. The only reachable desync is a missing record, and that self-heals — the next executor finds the step already applied. The reverse order permits a record with no change behind it, which makes real work get skipped. One direction is recoverable; the other is silent corruption.

Single writer per file

Writers are roles, not skills — the parent is one writer across all seven routes. Any output two workers could write at once is split into a unique artifact per writer, which is why the progress file, staged questions, report staging paths, and planner slots are shaped the way they are.

Checkout identity is explicit

Current working directory is never an identity. Every worker gets absolute main_root; task-bound workers also get one absolute worktree_path, allocated before the first source write and unchanged through diagnosis, retries, verification, recovery, and landing. A clean anonymous checkout is not the task checkout.

Work is checked, not claimed

A task’s test must be seen failing before the change, with the evidence recorded — a test written after the fix and never seen red proves nothing, and a reviewer in a fresh context cannot tell the two apart. The executor publishes one immutable range, a different agent verifies its head, and the lander merges that same head.

A wrong plan stays legible

Drift never patches or overwrites a task specification. The obsolete task becomes a terminal retired row, replacements get new ids and files, and the ledger records the immediate old-to-new relationship — or that no replacement is needed. Completed tasks remain completed history.

Ids are burned, never recycled

An unused, blocked, or interrupted reservation keeps its number, because a late worker may still hold its staging pointer. Gaps are permanent and correct. Spending numbers is cheaper than letting two detectors race for one filename.

Enforcement is prose, not walls

Agent definitions bought a tool allowlist and a model tier; skills buy portability. The trade is real and stated plainly: a verifier that could not edit is now a verifier that is told not to — so the skills relying on it say so at the top, in the places where breaking the rule would be easiest.
